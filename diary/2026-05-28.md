# 2026-05-28 — Week 3 — pre-S9 plumbing: kill the eval's two failure modes for good

## What was done

Phase 0 ship day. Pre-requisite for the S9 / S10 work — without an eval
that can actually reach `/chat`, the retrieval baseline I'm setting up
this week is impossible to measure. This is auth + DB plumbing (S3
material from Week 1) reopened because Week 2's eval surfaced both
failure modes simultaneously and last week's TEMP commits only widened
the bucket without fixing the cause. The goal was to fix the two specific failures from
last Saturday's eval (`HTTP 429` then `HTTP 401`) **permanently**, not
with another TEMP commit. By end of day the eval can hit `/chat`
indefinitely without competing with real users for the rate-limit
budget and without ever hitting a JWT expiry.

Applied from S9's "ingest + index pipelines should be idempotent and
re-runnable" framing: same property here for the eval runner — the
service-key path means a run can be Ctrl-C'd and re-started without
re-minting a token or re-applying for rate-limit headroom.

- **`EVAL_API_KEY` setting.** Single static string, empty default
  (feature off when unset). Set on Render's secret store; never in the
  repo. Rotatable in seconds (change env var → redeploy).
- **Service-key branch in `current_user`.** Before JWT decoding, check
  `secrets.compare_digest(token, settings.EVAL_API_KEY)`. On match,
  return a synthetic `eval@system.local` user that's lazy-created on
  first request with a `free` subscription. The user's
  `hashed_password` is a fixed sentinel string (`!eval-service-user-no-login!`)
  — not a valid bcrypt hash, so `verify_password()` always returns
  False and the eval user can never log in through `/auth/login` no
  matter what password is submitted.
- **`RateLimitMiddleware` overhaul.** Two changes. (a) The bucket key
  now reads `X-Forwarded-For` leftmost when present, falling back to
  `request.client.host`. Real clients behind Render's proxy finally get
  independent buckets — fixes the "global 600/60s ceiling" problem the
  May 21 diary called out. (b) When the request carries the configured
  `EVAL_API_KEY` bearer, the limiter short-circuits with
  `X-RateLimit-Bypass: eval` on the response. The downstream auth
  dependency still verifies the key, so this is a quota bypass, not an
  auth bypass.
- **`eval/run.py` accepts `--service-key` / `EVAL_SERVICE_KEY`.** Used
  verbatim as the bearer. No token mint, no expiry, no
  `refresh_token_if_expired()` wrapper to maintain. The existing
  `AUTH_TOKEN` JWT path stays for backward compat (and is now flagged
  in the docstring as "small runs only").
- **README extension.** New "Running the eval" section documents both
  auth modes side by side, with the quota-burn / expiry trade-off
  spelled out so future-me doesn't try to run a 51-question eval with a
  user JWT again.
- **12 new tests.** `tests/security/test_eval_auth.py` covers all four
  spec scenarios (valid key → eval user, disabled key → 401, wrong key
  → JWT fallback, eval user lazy-created once + gets a free
  subscription). `tests/security/test_rate_limit.py` covers
  X-Forwarded-For independence + eval-bearer bypass + wrong-bearer
  still gets bucketed. `tests/eval/test_run_cli.py` covers the new
  `--service-key` argparse path.

## Problems encountered

1. **Test environment didn't exist yet.** AI Lawyer's backend has no
   `conftest.py` or pytest config in the repo. Spinning up an
   in-memory DB for the auth tests meant getting SQLAlchemy + pgvector
   + bcrypt all importable without a real Postgres.
2. **`bcrypt 4.1+` breaks `passlib`'s version detection.** When I
   tried `pwd_context.hash(secrets.token_urlsafe(32))` for the eval
   user's hashed_password, the test crashed with
   `module 'bcrypt' has no attribute '__about__'` followed by a
   `password cannot be longer than 72 bytes` from a strict fallback
   code path. Known passlib bug.
3. **`app.models.__init__.py` transitively imports `Chunk`**, which
   imports `pgvector.sqlalchemy.Vector`. So importing any model in
   tests pulls pgvector — and SQLite (in-memory) can't host a `vector`
   column. The naive `Base.metadata.create_all(engine)` blows up.
4. **`SECRET_KEY` and `DATABASE_URL` validation runs at module import.**
   Set them wrong in the test env and the whole app refuses to load
   before any test fixture runs.

## Solutions

1. Wrote a minimal `backend/conftest.py` with a `db_session` fixture:
   in-memory SQLite, `StaticPool`, and `Base.metadata.create_all(engine,
   tables=[User.__table__, Subscription.__table__])` so only the auth
   tables are created (not chunks → no pgvector dependency in tests).
2. Sidestepped the bcrypt mess entirely by storing a fixed sentinel
   string for the eval user's `hashed_password`. The eval user can
   never log in through `/auth/login` (no password matches a non-bcrypt
   string) — exactly the property I want. Saved me from pinning
   `bcrypt<4.1` everywhere and from fighting `passlib`'s version
   detection.
3. Selective `create_all(tables=[...])` keeps the pgvector dependency
   out of test setup without changing the model layout. Production
   migrations still create the full schema.
4. `conftest.py` sets `os.environ.setdefault("DATABASE_URL",
   "postgresql+psycopg://test:test@localhost:65535/test")` and
   `SECRET_KEY="test-secret-key-for-pytest"` **before** any `app.*`
   import. The Postgres URL is syntactically valid so `create_engine`
   succeeds; no connection is ever attempted because every test that
   touches the DB receives the SQLite session via dependency override.

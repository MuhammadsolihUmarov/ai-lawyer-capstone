# 2026-05-26 — Week 3 kickoff: PM audit of the eval failure + 3-phase plan

## What was done

Spent the day **not coding**. Last week's eval run finished with `0/51`
answered, Recall@5 = 0%, and every quality axis N/A — exactly the
plumbing failure I half-expected when I left the rate-limit / JWT-expiry
notes in last Saturday's diary. The right next move wasn't to start
writing more features. It was to stop, audit, and write down a plan I
could actually execute end-to-end.

- **Re-read `docs/eval_report.md` line by line.** Q1–Q13 were `HTTP 429`
  (rate-limit). Q14–Q51 were `HTTP 401`. The flip from 429 to 401 mid-run
  is the smoking gun: the rate-limit retries (8s → 12s → 18s → 27s →
  40s, up to 6 attempts) ate so much wall-clock that the eval's user
  JWT expired (60-min TTL) by Q14. Both failures were diagnosed in the
  May 21 / 23 diaries; neither was actually fixed.
- **Drafted a 3-phase roadmap.** Phase 0 unblocks the eval signal (the
  prerequisite to any other measurement). Phase 1 establishes the
  retrieval baseline (Recall@5 ≥ 60 %). Phase 2 closes the answer-quality
  loop (groundedness ≥ 4.0). Mapped each phase to the S-rubric items it
  contributes to: Phase 0 → S3 (auth/DB), Phase 1 → S4 (RAG) + S13
  (eval), Phase 2 → S2 (LLM prompts) + S8 (guardrails).
- **Adopted OpenSpec discipline for the rest of the program.** Created
  `openspec/changes/phase-0-unblock-eval/` with proposal.md, tasks.md,
  and a spec delta under `specs/evaluation/`. The proposal uses RFC 2119
  keywords, Given/When/Then scenarios, and a concrete rollback plan
  (per the project's `config.yaml`). This is the discipline I keep
  saying I'll adopt and then ditch on the next sprint — the eval result
  pushed me hard enough that I actually wrote the proposal first this
  time.
- **Lined the plan up with Week 3's mentor sessions (S9 Ingestion / S10
  Embeddings & retrieval / S11 Generative + multimodal).** Phase 1 is
  effectively the S9 + S10 deliverable for AI Lawyer — a real seeded
  corpus + a measurable retrieval baseline. Phase 0 is upstream
  plumbing (S3 territory from Week 1) but it's the prerequisite for any
  measurement, so it has to land first.
- **Locked the embedding decision.** Local `.env` had
  `EMBEDDING_MODEL=BAAI/bge-m3`, `EMBEDDING_DIM=1024`. `config.py`
  defaults are `gemini-embedding-001`, `768`. Migration 0001 reads
  `EMBEDDING_DIM` at run time so production's column width is whatever
  Render had when the migration last ran. Picked **Gemini 768-dim** as
  the target: free-tier coverage, no 2.3 GB BGE-M3 download in the
  container, no extra RAM pressure on Render's slim dyno. Trade-off
  accepted: every chunk + every query embed hits Gemini's 15 RPM quota.
  Mitigation later — `GEMINI_API_KEYS` plural is already wired in
  `config.py` for rotation.

## Problems encountered

1. **I don't know what's actually in prod Neon.** Local `.env` and
   `config.py` defaults disagree on embedding dim (1024 vs 768). Render
   has its own env vars I can't see from here. If prod is on 1024 (BGE-M3)
   and I push code that assumes 768, the new chunks won't fit the column
   and ingestion will fail.
2. **No prod credentials in the repo.** Correct security-wise, but it
   means I can't simply connect a script and query the chunks table.
3. **The previous Week 2 TEMP commits never got reverted.** The
   "raise `/chat` cap to 600/60s" widening from the 23rd is still
   shipping. Behind Render's proxy that's effectively a global quota
   bucket — fine for me hammering it from one IP, terrible for real
   users.
4. **OpenSpec workflow isn't free.** Writing the proposal + tasks +
   spec delta added ~45 minutes before I touched a line of code. Past me
   would have skipped it. Today me forced through it because the 0/51
   result is what skipping the planning gets you.

## Solutions

1. **Don't guess prod state — measure it.** Phase 1 adds a `/health`
   extension that returns `embedding_provider`, `embedding_dim`,
   `chunks_count`, `documents_by_source`, `eval_key_configured`. Before
   any seed runs, the runbook checks `/health` and a `phase1_audit.py`
   tool. If the live dim doesn't match `settings.EMBEDDING_DIM`, the
   audit exits with a HALT and a separate `phase-1b-dim-migration`
   proposal is opened. No destructive writes against prod until the
   audit returns 0.
2. The Phase 1 runbook deliberately splits introspection (read-only,
   safe to share commands for) from destructive writes (gated, idempotent,
   `--dry-run` first). Operator runs each step from their own shell with
   their Render env exported — I never see the connection string.
3. The proper fix for the rate-limit / IP-bucket problem belongs in
   Phase 0, not as another TEMP commit. Plan: trust `X-Forwarded-For`
   leftmost so real clients get independent buckets, plus a static
   service-key path that bypasses buckets entirely for the eval runner.
4. The OpenSpec proposal is annoying but it pays back. Writing
   "**Success criteria:** `python -m eval.run --max 5` against prod
   returns 5/5 non-N/A scores" forces me to be specific about what
   "Phase 0 done" actually means. Without that, "Phase 0" becomes
   another aspirational sprint title.
